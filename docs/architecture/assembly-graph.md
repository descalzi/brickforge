# Assembly graph v1

BrickForge's assembly graph is the canonical record of a constructed model.
Each placed part is a node with a stable instance identifier, a real LDraw part
identifier, a colour code and a rigid transform in the LDraw coordinate frame.
Each graph edge records a pair of instances and the nominal connector feature
pairs that support their connection.

The version-1 JSON contract is defined in
[`schemas/assembly-graph-v1.schema.json`](../../schemas/assembly-graph-v1.schema.json).
The BOM has its own derived-data contract at
[`schemas/bom-v1.schema.json`](../../schemas/bom-v1.schema.json).

## Coordinate and placement convention

Translations and matrices are stored in LDraw Units (LDU), with the existing
LDraw convention: -Y points up. A placement matrix contains nine row-major
values, followed by its three-component translation. The same values are
written to the type-1 LDraw part reference.

Part identifiers are stored without a directory or extension. The initial
export writes each reference as `<part_id>.dat`, resolved by the user's LDraw
library. Colour codes are numeric LDraw colour identifiers.

## Graph construction and checks

`build_assembly()` accepts placed parts and the connection-profile catalogue.
It performs these deterministic checks:

1. Every instance identifier is unique and every part has a known profile.
2. Every transform is finite and orthonormal (including valid mirrored
   orthogonal transforms).
3. The nominal part-body envelopes do not interpenetrate.
4. Each pair of parts is checked by the stud/receiver matcher. A graph edge is
   recorded only when at least one feature pair aligns within the configured
   position tolerance and has opposing connector axes.
5. The resulting graph is connected. A one-part assembly is trivially
   connected.

The body-overlap test transforms the eight corners of a rectangular envelope
based on the profile's nominal footprint and body height, then compares the
resulting axis-aligned bounds. It is deliberately conservative for rotated
parts; it is not detailed triangle-mesh collision detection. Stud projections
and internal receiver geometry are not part of that body envelope.

The existing connection matcher supplies candidate stud-grid alignments. An
edge is therefore evidence of a nominal geometric interface only. Neither
this graph nor these checks prove clutch force, material behaviour, strength,
stability, or legal/approved building techniques. Those require richer
connection data and additional validation.

## Derived outputs

The `Assembly` object is the single source for all current outputs:

- **LDraw model:** one type-1 record per placed part, with the stored colour,
  translation and matrix.
- **Assembly JSON:** nodes and explicit graph edges, including each matched
  feature identifier, positional error and connector-axis dot product.
- **BOM JSON:** part quantities grouped by part identifier and colour.

This keeps the model and inventory consistent by construction. Build
instructions and sequencing are not generated yet.

## Browser execution

The public [Block builder](https://descalzi.github.io/brickforge/builder.html)
uses a browser-native implementation at
`docs/assets/construction-engine.js`. It consumes the same published
connection-profile JSON and creates the same version-1 graph, BOM and LDraw
records without calling a construction API. The visitor's browser performs
placement, feature matching, nominal body-envelope checks, graph connectivity
validation, 3D preview generation and file downloads.

The browser builder is intentionally independent of Python at runtime. Node's
built-in test runner executes the browser-safe engine module in CI and compares
its graph, BOM and LDraw model with the committed example generated by the
Python reference implementation. This parity check helps keep both paths
consistent.

The 3D preview uses nominal part envelopes and stud geometry for responsiveness.
The exported LDraw file references the real source part identifier; an LDraw
library is needed by a desktop viewer to resolve those references. Static site
hosting serves the HTML, JavaScript, CSS and catalogue only. No uploaded model
or generated assembly is sent to a remote service.

## Reproduce the examples

Install the development package from the repository root:

```bash
python -m pip install -e ".[dev]"
```

Run either demonstrator:

```bash
brickforge-demo-assembly
brickforge-demo-block
```

The first command validates two 3001 (Brick 2 x 4) instances: a red lower
brick at the origin and a blue upper brick translated by -24 LDU on Y. It
writes:

- `examples/stacked-3001.ldr`
- `examples/stacked-3001.assembly.json`
- `examples/stacked-3001.bom.json`

The second command is also a local developer/reference tool. It exercises the constrained construction strategy. Its 4 x 4-stud example uses four 3001 parts in two courses. The upper course rotates the two bricks 90 degrees about Y so each bridges the seam between the two lower bricks. Each upper brick has four nominal feature matches to each lower brick, producing four graph edges and 16 feature pairs. It writes:

- `examples/block-4x4x2.ldr`
- `examples/block-4x4x2.assembly.json`
- `examples/block-4x4x2.bom.json`

The reusable `build_rectangular_block()` strategy accepts width and depth in
studs and height in brick courses. It has three staggered upper-course layouts:

- For a footprint wider than 4 studs and exactly 4 studs deep (for example,
  12 x 4), rotated 3001 (2 x 4) bricks bridge the lower columns. Four 3004
  (1 x 2) parts close the side strips in the 12 x 4 example.
- For a 4-stud-wide footprint deeper than 4 studs (for example, 4 x 8), the
  upper 3001 bricks are staggered along depth and 3004 parts close the ends.
- When both dimensions exceed 4 studs (for example, 12 x 8), the upper 3001
  core is shifted by half a brick in X and half a row in Z, bridging the lower
  joints in both directions. The one-stud perimeter strips are tiled with
  standard-orientation 3004 parts.

The 12 x 8, two-course block contains 12 lower 3001 parts, six upper 3001
core parts and 24 upper 3004 perimeter fillers: 42 elements in total. Its
graph has 48 edges and 96 nominal mating pairs. These layouts pass the
connected-graph and nominal body-envelope checks without interpenetration.
Other dimensions remain constrained by available tiling patterns; the
strategy does not yet search arbitrary part combinations or cover irregular
shapes.
